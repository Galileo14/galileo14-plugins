## Verdict

The skill is sound. All three controls it needs — Input, Output, Speed — are present, correctly wired, and well built: the framework specs are complete with worked examples and anti-patterns, the output template is a real `{{SLOT}}` fill-in with a strip-comment step, and the three framework-applier subagents are dispatched as unregistered nested agents with `model: sonnet` set explicitly at Task-call time (the correct pattern for skill-nested agents, and it is followed correctly here — the scan's `agents_missing_model` flag is a false positive for this design). ## Skill profile

What it does: turns a raw user request into a polished, framework-structured prompt (CAR, COSTAR, or RISEN), rendered into a fixed template and printed as the entire chat response.

Nature (drives which controls are needed):
- Input variability: low — the three framework specs are fixed, authoritative, versioned reference docs, not fetched from anywhere volatile.
- Process: partly fixed, partly novel — framework *selection* (Rule 1 token matching) is deterministic; framework *application* (writing the actual prompt) is genuinely creative/novel each run.
- Output: fixed shape — one canonical template (`assets/output-template.md`) with named slots, structure and headings must not change.
- Parallelisable work: none needed — exactly one framework is applied per run by design ("one framework per run"), so there is no independent unit to fan out.
- Correctness risk: low — a human (the requesting user) reads and judges the single rendered prompt every run before using it elsewhere; no unverified factual claims are made.
- Runtime and scaling: short — 4 sequential steps, one subagent dispatch, no fan-out; wall-clock is dominated by one Sonnet subagent call.
- Length and resumability: short — step count 4, well under the ~8-step threshold where checkpointing becomes relevant.

- **Assessment:** correctly scoped — only one framework runs per invocation by design ("Never mix frameworks... One framework per run", `SKILL.md:84`), so there is no independent parallel unit to fan out; three agent files existing but only one dispatched per run is not a missed-parallelism opportunity, it is the router pattern working as intended. ## Potential security vulnerabilities

- **Prompt-injection via pasted "improve this prompt" content:** the "user pastes an existing prompt and says 'improve this'" edge case (`references/framework-detection.md:59`) hands arbitrary user-supplied text straight into `raw_request`, which becomes the applier subagent's working material. Nothing in `SKILL.md` or the agent files tells the subagent to treat that text purely as content, not instructions — low stakes (the user can only attack their own session), but worth closing.
  - Fix: add the one-line guard from Prioritised Improvement #3 above to each `agents/*-applier.md` file.
- No secrets, API keys, or credential material found in any file (`SKILL.md`, agent files, references, assets). No dangerous defaults (no delete/overwrite/destructive action anywhere in the skill). No external MCP/connector dependency to declare — `AskUserQuestion` is a core tool, not an external connector.

## Potential parallelisation opportunities

Genuinely nothing to parallelise. The skill is single-request, single-framework, single-subagent by design ("One framework per run", `SKILL.md:84`) — the three applier agents are alternatives selected by a router, not independent units that could run concurrently. Fanning out all three "just in case" would waste tokens computing two prompts the user never asked for and violate the skill's own hard rule against mixing frameworks.
