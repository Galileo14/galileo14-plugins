# Skill audit: g14-skill-creator

**Target:** `/Users/pablovgdev/g14/projects/galileo14-plugins/plugins/ai/skills/g14-skill-creator`
**Audited:** 2026-07-09 · single-pass manual audit against the five-controls rubric (no separate grader pass this run)
**Conformance:** Adequate (1 P1 gap, 2 P2 issues, 2 P3 polish items)

## Verdict

The skill is well-built for what it actually is: an interactive, human-in-the-loop
workflow that teaches and scaffolds the five-controls framework, not an automated
pipeline. Controls 1 and 3 are present, wired, and genuinely needed; Controls 2
and 5 are correctly skipped for the creator's own run because the work is
judgment-driven and the user reviews every step. The one real defect is
structural rather than cosmetic: the Control-5 wiring this skill hands to every
skill it scaffolds hardcodes a path back into g14-skill-creator's own plugin
folder for the grader contract, which only resolves when the new skill happens
to live in the same plugin. In a marketplace that already has a dozen separate
plugins, most skills built with this tool will inherit a broken grader
reference. Fix that first; the effort-field gap on the grader and the missing
"where will this skill live" interview question are smaller, related issues
worth cleaning up in the same pass.

## Skill profile

What it does: interviews the user to scaffold a new Claude Code skill, decides
which of the five controls the new skill needs (starting from zero), and builds
the artifacts plus the `SKILL.md` wiring for it.
Nature (drives which controls are needed):
- Input variability: low for the creator itself — its own inputs are two pinned
  reference files (`five-controls.md`, `decision-table.md`) it always reads the
  same way. High for the skills it produces, which is exactly what Control 1
  guidance exists to pin.
- Process: novel each run — every scaffolded skill is a different interview and
  a different set of artifacts; nothing here is deterministic work re-reasoned
  in prose.
- Output: fixed shape for the top-level `SKILL.md` (via `assets/skill-md-skeleton.md`);
  adaptive for the deeper per-skill artifacts (source files, scripts, criteria
  files), which is appropriate since those are content-specific to whatever is
  being built.
- Parallelisable work: none in the creator's own six-step run — it is inherently
  sequential (interview → draft → diagnose → build → wire → verify).
- Correctness risk: low for the creator's own output — the user is present for
  the whole interactive build and Step 6 has them drive 2-3 real prompts before
  calling it done. The human is the grader.
- Runtime and scaling: short, single-session, no external fetches or fan-out; no
  wall-clock concern.
- Length and resumability: 6 steps, well under the ~8-step threshold where
  checkpointing would be recommended.

## Per-control findings

### Control 1: Input
- **Status:** PRESENT+WIRED+NEEDED
- **Evidence:** `references/five-controls.md`, `references/decision-table.md`; wired at `SKILL.md:49-50` ("Read it before building any control") and again at `SKILL.md:98-100`, `SKILL.md:127-128`.
- **Assessment:** Exactly the shape the framework itself recommends — one file per concept, each pointed to explicitly and re-used across multiple steps rather than duplicated inline. No drift risk: these are the tool's own fixed rulebook, and nothing here should vary run to run.
- **Recommendation:** None, correct as is.

### Control 2: Process
- **Status:** ABSENT+NOT-NEEDED → correct skip
- **Needed because / Skip is correct because:** Per the decision table's own skip condition ("the task is genuinely novel each run"), the creator's real work — interviewing the user, diagnosing which controls apply, drafting artifacts specific to whatever skill is being built — is judgment work with no single repeatable "how." There is no deterministic fetch/dedupe/rank/validate step being re-reasoned in prose here.
- **Assessment:** Correct skip for the bulk of the workflow. See P3 finding below for one small mechanical sliver (folder scaffolding) that could still be scripted without contradicting this.
- **Recommendation:** None required; optional P3 improvement noted in Prioritised improvements.

### Control 3: Output
- **Status:** PRESENT+WIRED+NEEDED
- **Evidence:** `assets/skill-md-skeleton.md`; wired at `SKILL.md:85-88` ("Use ... as the starting shape").
- **Assessment:** A real `{{SLOT}}`-style template with a trailing HTML comment block that maps each control to its one-line wiring pattern — good, reusable, keeps `SKILL.md` lean by not inlining the wiring cheatsheet. One gap: the rubric requires Control 3 to also pin *where* the deliverable lands. `SKILL.md` never asks or states where the new skill folder should be created (inside which plugin's `skills/` dir, `.claude/skills/`, or `~/.claude/skills/`) — see the P2 finding below, since this also causes the Control-5 wiring bug.
- **Recommendation:** Add an explicit destination step (see finding #3 below); otherwise the template itself needs no change.

### Control 4: Speed
- **Status:** PRESENT+WIRED, repurposed (not a gap — matches the scorecard legend's explicit allowance for a control present-but-serving-another-control's-purpose)
- **Evidence:** `agents/grader.md` is the only file in `agents/`; it is the Control-5 grader contract, not a parallel Speed worker for the creator's own run. Wired via `SKILL.md:147-149` and the Control-5 section of `references/five-controls.md:281-305`.
- **Needed because / Skip is correct because:** The creator's own six steps are strictly sequential (each depends on the previous), so there is no independent work of its own to fan out. `agents/` is correctly used here as the shared home for the reusable grader instruction file that Control 5 (in every *scaffolded* skill) depends on.
- **Assessment:** Reasonable and intentional reuse of the folder convention. The one real defect is not that this folder exists, but *how it is referenced from outside its own plugin* — see the P1 finding below.
- **Recommendation:** See P1 finding (grader cross-plugin reference).

### Control 5: Tests
- **Status:** ABSENT+NOT-NEEDED (for the creator's own output) → correct skip
- **Needed because / Skip is correct because:** Decision table's explicit skip condition: "a human reviews every run anyway — the human IS the grader." Step 1 is a live interview, Step 3 has the user co-sign the controls decision, and Step 6 has them run 2-3 real prompts end to end before treating the new skill as done. Nothing in the creator's own deliverable is a wrong-but-plausible claim a fresh grader would need to catch; it's a collaboratively-built artifact reviewed in real time.
- **Assessment:** Correct skip. Separately, the skill teaches Control 5 very well for the skills it *produces* — but see the P1 and P2 findings, both of which live inside that Control-5 teaching material.
- **Recommendation:** None for the creator's own tests/. Fix the grader contract itself (below).

## Cross-cutting findings

- **Triggering / description:** Strong. 103-word description lists concrete trigger phrases ("create a skill", "build a skill that doesn't drift", "make a reliable/repeatable skill", "apply the five controls", "deterministic skill") and names the adjacent case it should win over (a generic skill draft). No mis-trigger risk seen.
- **Authoring (instructions, WHY, failure modes, magic values):** Mostly strong — every step states its rationale (e.g. "This is deliberate: a skill that works fine as one file doesn't need scaffolding"). One self-consistency gap: `SKILL.md` has a "## What this does" section (line 8) but no "## When to use it" section, even though `assets/skill-md-skeleton.md` (the very template this skill hands to every skill it scaffolds) requires exactly that section (skeleton lines 15-18). See P3 finding.
- **Preflight / fail-fast:** N/A. The skill's only hard dependencies are its own vendored reference/asset files, and the scan confirms zero broken referenced paths. It has no external tool, MCP, credential, or user-input-file dependency to check, and at 6 steps it is not long or expensive enough to warrant a dedicated preflight step.
- **Error handling (retries / fallbacks / stop-steps):** N/A for the creator's own run — it's a live, collaborative session, not an unattended pipeline with steps that can silently fail. The advice it gives *downstream* skills about escape hatches and fallbacks (Step 4, Control 2 bullet) is sound.
- **Process artifacts (scripts pre-stored, not generated on the fly):** N/A, no `scripts/` folder and none needed for the reasons in the Control 2 finding above. `signals.writes_scripts_on_the_fly` is false — the skill never tells Claude to author a script at run time either.
- **Output storage (deterministic destination + naming, or DB):** Gap — see P2 finding #3. The skill pins the *shape* of the new `SKILL.md` (Control 3) but never pins or asks about *where* the new skill folder is created, which plugin (if any) it belongs to, or what determines whether `${CLAUDE_PLUGIN_ROOT}`-style paths are even valid for it.
- **Intermediate state / checkpointing:** N/A. `step_count` is 6, well under the ~8-step threshold, and the whole thing runs in one interactive session with the user present, so there's nothing to resume across a compaction.
- **Packaging (plugin/routine):** Not a routine. `${CLAUDE_PLUGIN_ROOT}` usage is otherwise correct and consistent (5 uses, 0 hardcoded absolute paths) for the creator's own files — the defect is specifically that it also tells *downstream* skills to reuse this same plugin-relative path back into g14-skill-creator's own folder, which is a packaging mistake in the artifact this skill produces. See P1 finding.

| 1 | P1 | Control 5 wiring / packaging | Every skill scaffolded by this tool is told to point its grader subagent at `${CLAUDE_PLUGIN_ROOT}/skills/g14-skill-creator/agents/grader.md` (`SKILL.md:147-149`, `references/five-controls.md:299-300`). `${CLAUDE_PLUGIN_ROOT}` resolves to the plugin that *owns the file being read* — i.e. the new skill's own plugin — not g14-skill-creator's.
