# Skill audit: g14-scalability-audit

**Target:** `/Users/pablovgdev/g14/projects/galileo14-plugins/plugins/audit/skills/g14-scalability-audit`

## Verdict

The skill is a clean, correctly-scoped thin runner: it resolves a target, dispatches the one `scalability-auditor` Task call it needs, fills a fixed template, and reports back tersely. It respects the plugin's thin-runner rule properly — no lens content leaked into SKILL.md, the agent's model/effort/tools are explicitly left untouched. The one real defect is a numeric mismatch between SKILL.md ("pick the top 3 findings") and the template's 5-row "Top findings" table, which will either leave unfilled `{{SLOT}}` placeholders in delivered reports or force the model to improvise past the "template is the contract" rule — fix by trimming the template to 3 rows. Beyond that, the only gaps are the usual short-runner omissions: no explicit handling for the single Task call failing or returning malformed output, and no instruction telling the agent to treat file content read from the target codebase as data rather than instructions (a latent prompt-injection exposure shared by all five audit agents, not unique to this skill). Nothing here breaks a run today; all three P2s are worth a few minutes each.

## Skill profile

What it does: resolves a target codebase path, invokes the plugin-root `scalability-auditor` agent once via `Task`, and writes its findings into a fixed markdown report at a deterministic path.
Nature (drives which controls are needed):
- Input variability: none owned by this skill — the lens (what to check) is owned entirely by the shared `scalability-auditor` agent; this skill's only "input" is the target path, resolved fresh each run.
- Process: fixed, tiny (4 inline bash lines for path/timestamp resolution) plus one Task dispatch; not complex enough to warrant a committed script.
- Output: fixed shape — `assets/report-template.md` with `{{SLOT}}`s, saved to a deterministic `reports/scalability-audit-<timestamp>.md`.
- Parallelisable work: none — a single Task call is the entire unit of work; nothing else to fan out.
- Correctness risk: real (a scalability audit can misjudge severity or miscite a location) but advisory — a human reads the report before acting on it, and grounding comes from the agent's own Read/Grep/Glob/Bash use against real files, not open-web claims.
- Runtime and scaling: one Task dispatch (seconds to a couple of minutes depending on codebase size) plus three cheap local steps; no large or unbounded fan-out.
- Length and resumability: 4 steps, no checkpointing warranted.

## Potential security vulnerabilities

- **Latent prompt-injection exposure via target codebase content:** the `scalability-auditor` agent (dispatched by this skill) reads arbitrary file content from `target_path` with `Read`/`Grep`/`Glob`/`Bash` and no instruction to treat that content as inert data. A codebase containing adversarial text (a comment, a string literal, a README) aimed at the auditor could bias or suppress findings.
  - Fix: add the one-line guard described in prioritised item #3 to the shared agent file (not to this skill — the agent is the single source of truth for its own read discipline per the thin-runner architecture).
- No secrets, API keys, or credential material found in any file under this skill (`SKILL.md`, `assets/report-template.md`). No dangerous defaults (delete/overwrite without confirmation) present — the skill only ever calls `Write` to a path inside `$TARGET/reports/`, computed deterministically, not an arbitrary or user-overridable location.
