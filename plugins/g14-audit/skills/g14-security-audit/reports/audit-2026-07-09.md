# Skill audit: g14-security-audit

**Target:** `/Users/pablovgdev/g14/projects/galileo14-plugins/plugins/audit/skills/g14-security-audit`
**Audited:** 2026-07-09 · single-pass manual audit (no multi-grader quality gate this run)

## Verdict

The skill is a clean, correctly-built thin runner: it resolves a target, dispatches the plugin-root `security-auditor` agent without touching its fixed model/effort/tools, and fills a well-designed fixed report template at a deterministic path. The two real problems are (1) the inline bash that resolves the target path has no fail-fast guard, so a bad path silently produces `mkdir -p "/reports"` at the filesystem root instead of stopping, and (2) the skill ships security findings — inherently wrong-but-plausible claims (file:line citations, severity, vulnerability descriptions) — straight to the user with no fresh-context grounding check, which is exactly the case Control 5 (Tests) exists for. Neither issue requires touching the lens content in `agents/security-auditor.md`; both are fixable inside this skill's own files.

## Skill profile

What it does: resolves a target codebase path, dispatches the plugin-root `security-auditor` agent (sonnet, effort high, Read/Grep/Glob/Bash) for a single-lens OWASP-shaped security audit, and consolidates its verbatim findings into `assets/report-template.md`, saved to `<target>/reports/security-audit-<timestamp>.md`.

Nature (drives which controls are needed):
- Input variability: none owned by the skill — the target codebase is freely explored by the agent; no fixed source list to pin.
- Process: fixed method (one `Task` call, exact prompt template, exact bash for path/timestamp resolution) — appropriately pinned in prose, not re-reasoned each run.
- Output: fixed shape — a literal `{{SLOT}}` template with a deterministic destination and filename convention.
- Parallelisable work: none — single target, single lens, one agent call. Nothing to fan out.
- Correctness risk: real. The agent's findings are file:line-grounded vulnerability claims that could be wrong-but-plausible (wrong location, fabricated issue, mis-graded severity), and the report is typically consumed without a human re-verifying every citation.
- Runtime and scaling: fast — 4 steps, one subagent dispatch, no fan-out. Wall-clock dominated by the single agent's exploration of the target repo.
- Length and resumability: short (4 steps) — no checkpointing needed.

### Control 5: Tests (`tests/`)
- **Status:** ABSENT+NEEDED → GAP
- **Evidence:** scan: `5_tests.present: false`, `signals.mentions_grader_or_fresh_context: false`. SKILL.md's 4-step pipeline goes straight from "3 · Consolidate the final report" (paste the agent's findings verbatim) to "4 · Report back" — no verification step in between.
- **Needed because:** per the decision table, Control 5 is needed "when the output makes claims that could be wrong-but-plausible... AND no human reviews every run." A security audit report is exactly that: each finding asserts a specific `path/to/file.ext:line` and a vulnerability description that could be hallucinated, mis-located, or mis-graded by the LLM producing it, and the skill delivers the report as a finished deliverable with only a 4-line chat summary — nothing in the pipeline forces a human to check every citation before the report is treated as authoritative. The agent's own "Analysis must be specific and grounded in what you actually read" instruction and its per-finding `Confidence: high|medium|low` field are good producer-side discipline, but they are self-reported by the same agent that produced the claim — not an independent check, and the rubric is explicit that a producer grading (or here, merely asserting confidence about) its own work doesn't satisfy Control 5.
- **Assessment:** genuine gap. This is not unique to this skill — all four sibling thin-runner audit skills (`g14-scalability-audit`, `g14-architecture-audit`, `g14-clean-code-audit`, `g14-database-audit`) share the identical 4-step shape and the identical absence of a verification step, so this is a systemic pattern in the plugin, not a one-off mistake in `g14-security-audit`. That doesn't change the verdict for this skill on its own, but it means the fix is best made once and applied consistently.
- **Recommendation:** add a verification step between "3 · Consolidate" and "4 · Report back" that does NOT touch lens content (severity rubric, categories stay in the agent — architecture-compliant). Concretely: dispatch one fresh `general-purpose` subagent (`model: sonnet`, `effort: low`, `tools: Read, Grep, Glob` — no Bash, no Write) with only the consolidated findings' `Location` + `Description` fields and `target_path`, asking it to confirm each CRITICAL/HIGH finding's cited file:line exists and plausibly matches the description, returning a short PASS/FLAG list. If any finding is flagged, keep it in the report but mark `Confidence: low (unverified location)` rather than dropping it silently. This is a single new paragraph in SKILL.md plus, if the same rubric will be reused by the sibling skills, one shared grader prompt — it does not require a `tests/` folder the size of `g14-skill-audit`'s.
