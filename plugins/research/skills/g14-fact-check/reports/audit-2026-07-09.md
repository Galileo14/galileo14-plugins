## Verdict

The skill is sound and correctly thin: it captures the claim, plans 10 evidence
angles, fires the fan-out in one message, and hands synthesis to the shared
`research-synthesizer` agent, exactly as the plugin's thin-orchestrator
architecture prescribes. Controls 1-3 are correctly, deliberately absent (open
web exploration, tool calls pinned by exact params in prose, and a short inline
template are all legitimate skips for this shape of skill). Control 4 is
present and well executed via plugin-root agents. The real gaps are all
best-practice items, not five-controls gaps: there is no fresh-context check on
the verdict before it's rendered (the skill leans on the producer's own
heuristic fabricated-source filter), no handling for a `Task` dispatch itself
failing among the 10 parallel calls, and no prompt-injection guard on the
open-web content the evidence angles fetch. None of these break a normal run
today; all three are worth fixing before this is used for higher-stakes
verdicts.

## Skill profile

What it does: verifies a factual claim by dispatching 10 parallel `web-searcher`
Task calls (one per evidence angle), then aggregates the inline reports into a
structured True/False/Misleading/Partially True/Insufficient Data verdict via
`research-synthesizer`. All-inline, no files written.

Nature (drives which controls are needed):
- Input variability: open-ended — any claim, any topic; sources come from live
  web search, not a fixed feed or API.
- Process: fixed method captured as exact `Task` params in prose (topic,
  queries, angle, output_mode, language, source_tier_filter) — deterministic
  enough without a script, per the "process pinned" exception.
- Output: fixed shape (🔍/⚖️/📝/📚 block), short enough to live inline in
  `SKILL.md` rather than as a separate template file.
- Parallelisable work: yes, and already exploited — 10 independent evidence
  angles fanned out in one message.
- Correctness risk: high in principle (a definitive True/False verdict is a
  wrong-but-plausible risk) but mitigated by the interactive medium — the user
  reads the verdict immediately and can push back, unlike an unattended file
  deliverable.
- Runtime and scaling: ~30-60s dominated by the slowest of 10 parallel Haiku
  `web-searcher` calls, then one Haiku synthesizer call. No large/unbounded
  fan-out; plain parallel dispatch is the right mechanism, already used.
- Length and resumability: 5 steps, single round-trip — too short to need
  checkpointing.

### Control 3: Output (`assets/`)

### Control 4: Speed (`agents/`)
- **Status:** PRESENT+WIRED+NEEDED
- **Evidence:** SKILL.md step 3 (lines 64-76): "the 10 `Task` calls must be emitted in the **same assistant turn**, in a single block"; dispatches `subagent_type: web-searcher` (plugin-root registered agent, `model: haiku`, `effort: low` per its own frontmatter) with a scoped prompt (topic/queries/angle/output_mode/language/source_tier_filter — not the whole conversation); each worker returns `output_mode: inline`, a structured report, not a transcript. Step 4 dispatches one `research-synthesizer` (`model: haiku`, `effort: medium`).
- **Assessment:** done well. No missing fan-out opportunity — the two stages (10 independent searches, then 1 dependent synthesis) are already maximally parallel given the real dependency between them. Model/effort are inherited correctly from the plugin-root agent's own frontmatter and never overridden, matching the plugin norm that skills never re-state or escalate agent-level model/effort. No local `agents/` folder is needed or expected here since the agents are plugin-root and shared across 3 skills (`web-searcher`) — nesting them in this skill would violate the plugin's no-duplication rule.
- **Recommendation:** none, correct as is.

### Control 5: Tests (`tests/`)
- **Status:** ABSENT, borderline-NEEDED → present-but-weak
- **Evidence:** scan: `5_tests.present: false`. SKILL.md line 18: "URL-level validation (`source-validator`) is intentionally NOT used here — g14-fact-check is inline-only and the synthesizer already drops fabricated-looking sources during verdict assembly." The plugin's own `plugins/research/CLAUDE.md` lists `g14-fact-check`'s agent chain as ending in "→ optional `source-validator`" — directly contradicting SKILL.md's blanket exclusion; no optional path exists anywhere in the 5 steps.
- **Needed because / Skip is correct because:** genuinely borderline. The decision-table trigger ("facts traceable to sources... AND no human reviews every run") points toward NEEDED — a False/True verdict is exactly the "wrong-but-plausible" claim type the control exists for, and `research-synthesizer`'s own fabricated-source filter (`research-synthesizer.md` step 4: "if a domain looks invented... drop it") is a lexical heuristic run by the same agent that produced the verdict, not an independent fetch-based check — this is precisely the "producer grades itself" anti-pattern the best-practices checklist calls out. What tips it back from a hard gap: the output is delivered inline and read by the user immediately, giving a real (if informal) human-in-the-loop check that a saved file (like `g14-company-analysis`'s HTML dossier) doesn't get.
- **Assessment:** present-but-weak — no fresh-context check exists, the skill's own justification conflates a producer heuristic with independent verification, and the stated design ("optional source-validator") in the plugin's architecture doc isn't actually implemented in this skill.
- **Recommendation:** add an optional Step 6 that fires the existing `source-validator` agent (no new agent needed) specifically when the verdict is **True** or **False** — the two highest-consequence outcomes — checking that the "Sources consulted" list is reachable and on-domain, run in fresh context before the final render. Keep it skipped for Misleading/Partially True/Insufficient Data, where the verdict already signals lower confidence. Update SKILL.md line 18 to describe this conditional path instead of a blanket exclusion, resolving the drift against `plugins/research/CLAUDE.md`'s own "optional source-validator" claim.
