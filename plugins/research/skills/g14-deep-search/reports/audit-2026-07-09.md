# Skill audit: g14-deep-search

**Target:** `/Users/pablovgdev/g14/projects/galileo14-plugins/plugins/research/skills/g14-deep-search`
**Audited:** 2026-07-09 · single-pass (no separate multi-grader quality gate this run)
**Conformance:** Strong (0 gap(s), 1 correctness issue(s), 3 polish item(s))

## Verdict

The skill is a well-built thin orchestrator that matches the research plugin's
documented architecture almost exactly: it captures the topic, plans 10×5
queries, fires 10 `web-searcher` calls in one message, synthesizes via
`research-synthesizer`, and optionally quality-gates via `hallucination-grader`
+ `source-validator` — all agent parameters match the callee agents' documented
inputs, and the pass/fail thresholds it quotes (13/15, 90%) are copied verbatim
from the graders' own contracts. All five controls are either correctly
present or correctly, deliberately skipped given this skill's nature (open
topic, no fixed sources, no local template needed since format lives in
`research-synthesizer`). The one real gap: failed-angle relaunches have no
retry cap, so a persistently broken search angle could be relaunched forever
instead of being marked skipped. Everything else is polish.

## Skill profile

What it does: fans out 50 web searches (10 angles × 5 queries) via 10 parallel
`web-searcher` subagent calls, consolidates the findings into one 3000-5000
word markdown report via `research-synthesizer`, and optionally runs two
fresh-context quality graders before presenting the result to the user.

Nature (drives which controls are needed):
- Input variability: open-ended — topic is arbitrary, sources are the open
  web, nothing to pin to a fixed whitelist.
- Process: query-planning is genuinely novel per topic (can't be scripted);
  the deterministic parts (search execution, dedup, anti-hallucination rules,
  synthesis format) are already pinned in plugin-root agents, not re-reasoned
  in prose here.
- Output: fixed shape (markdown, 3000-5000 words, fixed sections) but that
  shape is owned by `research-synthesizer`, not this skill.
- Parallelisable work: yes, maximally exploited — 10 independent searches in
  one message, 2 independent graders in one message.
- Correctness risk: real (web research can surface wrong-but-plausible
  claims), covered by an optional grader pair, default-off for speed by
  explicit plugin design.
- Runtime and scaling: ~10 parallel `web-searcher` calls (capped at 2
  WebFetch each) + 1 synthesizer + optional 2 graders in parallel. Estimated
  wall-clock a few minutes, already parallelised — no missed win found.
- Length and resumability: 6 phases; the findings-file layout doubles as a
  checkpoint (file presence = phase done), and a "Resume after interruption"
  section reads that state back. Adequate for this skill's length.

### Control 3: Output (`assets/`)

### Control 4: Speed (`agents/`)
- **Status:** PRESENT+WIRED+NEEDED
- **Evidence:** SKILL.md:73-88 dispatches 10 `web-searcher` `Task` calls "in the same assistant turn, in a single block"; SKILL.md:104-107 dispatches `hallucination-grader` + `source-validator` "in parallel in a single message". All four `subagent_type` names match real, plugin-root-registered agents (`plugins/research/agents/web-searcher.md`, `research-synthesizer.md`, `hallucination-grader.md`, `source-validator.md`), not skill-nested files, so the registration caveat doesn't apply. All parameters passed (topic, queries, angle, output_mode, output_path, language, max_fetches / findings_paths / findings_dir / verdict_path) match each agent's documented input contract exactly — no broken wiring.
- **Assessment:** well-built. Fan-out is a fixed, bounded 10 units (not large/unbounded, so plain parallel dispatch is the right mechanism, not a dynamic Workflow). Model selection is correctly deferred to the agents (all four are pinned `haiku` in their own frontmatter); the skill's only stated model override is a one-off, explicitly-reasoned escalation to `sonnet` for a single failing synthesizer retry (SKILL.md:149), which matches the plugin's documented allowance ("skills may escalate a single failing call... but never default to it").
- **Recommendation:** none, correct as is.

### Control 5: Tests (`tests/`)
- **Status:** PRESENT+WIRED+NEEDED (conditionally applied by design)
- **Evidence:** SKILL.md:102-111 fires `hallucination-grader` + `source-validator` — both fresh-context graders, never the producer grading itself — gated behind "high-stakes research" or explicit user request, and skipped by default "prioritizes speed" (SKILL.md:111). Thresholds quoted (`pass < 13/15`, `(ok+ok_gated) < 90%`) match the graders' own documented orchestrator-decision contracts verbatim (`hallucination-grader.md` line ~75, `source-validator.md` line ~80).
- **Needed because:** web research produces wrong-but-plausible claims and no human independently checks every run's sources.
- **Assessment:** correctly delegated (fresh context, correct model/effort inherited from the agents) and correctly optional per the plugin's documented speed-over-verification default for this skill. One under-implementation: `source-validator`'s own doc defines three response tiers for the orchestrator (≥90% pass, 70-89% deliver-with-warning, <70% don't-deliver/relaunch worst angles), but this skill's Phase 5 only implements a single response ("flag the weak claims/URLs in the presentation message") for any failure, regardless of how bad the reachability ratio is.
- **Recommendation:** in Phase 5, branch on the `source-validator` ratio: if `(ok+ok_gated)/total < 70%`, say so explicitly and offer to relaunch the worst-performing angles, instead of only flagging weak URLs in prose. (P3 — this only matters on the already-optional, high-stakes path.)
