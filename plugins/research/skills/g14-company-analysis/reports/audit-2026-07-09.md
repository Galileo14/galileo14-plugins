## Verdict

The skill is well-built as an orchestrator: it correctly holds no methodology
of its own, fans the 11 platform researchers out in one message, fires the two
mandatory graders in one message, and applies a clear numeric verdict before
delivery. Nothing is broken today — every referenced path resolves and the
five-controls split (agents own the lens, this skill owns the plan) matches
the plugin's documented architecture exactly. The one thing worth fixing first
is that Phase 2 through 4 spend real time and tokens (11 live web researchers)
before the skill ever confirms its own template asset is intact, so a damaged
template would only surface after the expensive part of the run is already
done. A second real issue: the banner template's own inline comment describes
a different mechanism than the one the synthesizer agent and Phase 5 actually
use, which risks the warning banner silently not appearing on a "pass with
warnings" report.

## Skill profile

What it does: captures a company name/domain, fans out 11 platform-specific
researcher agents in parallel, synthesizes their findings into a fixed
branded HTML template, runs two fresh-context quality graders in parallel,
and applies a verdict (deliver clean / deliver with warnings / withhold).

Nature (drives which controls are needed):
- Input variability: none at the skill level — the skill never itself fetches
  facts; all source-of-truth methodology (query syntax, source tiers,
  anti-hallucination rules) lives in the 11 platform-researcher agents at the
  plugin root, by design.
- Process: fixed method, same every run (phase table, verdict thresholds,
  resume logic) — the "process" is orchestration prose, not data
  transformation, and is small enough that it doesn't need a script.
- Output: fixed shape — a single branded HTML file filled from a `{{SLOT}}`
  template, written to a deterministic path (`research/{slug}/{slug}.html`).
- Parallelisable work: two independent fan-outs, both already correctly
  parallel — 11 platform researchers (Phase 2) and 2 graders (Phase 4).
- Correctness risk: high — the report makes concrete, wrong-but-plausible
  factual claims (ratings, funding, headcount, quotes) with no human review
  before delivery, which is exactly why Control 5 is mandatory here.
- Runtime and scaling: 11-way parallel fan-out of live web research (roughly
  2-5 min wall clock) + synthesis (~1 min) + 2-way parallel grading (~1-2 min,
  each grader does its own per-claim/per-URL `WebFetch` calls) — a genuinely
  expensive run, correctly kept parallel at both fan-out points; no large or
  unbounded fan-out (the platform count is fixed at 11), so no dynamic
  Workflow is warranted.
- Length and resumability: 6 phases, not deep enough to need generic
  `state.json` checkpointing, but the skill already ships a purpose-built
  resume mechanism (missing-file detection by numeric prefix) that covers the
  same need better than generic checkpointing would.

## Per-control findings

### Control 1: Input (`references/`)
- **Status:** ABSENT+NOT-NEEDED → CORRECT SKIP
- **Evidence:** `scan_skill.py` reports `1_input.present: false`. `SKILL.md` never fetches facts itself; Phase 2 delegates all sourcing to 11 named plugin-root agents.
- **Skip is correct because:** per the decision table, Control 1 is needed when the skill itself pulls facts from sources that vary or must be pinned. This skill's job is orchestration only — the source taxonomy and per-platform query rules live in `plugins/research/agents/*-researcher.md`, one file per platform, which is the correct owner per the plugin's thin-orchestrator architecture (`plugins/research/CLAUDE.md`). Duplicating any of that into this skill's `references/` would violate the "agents own, skills compose" rule.
- **Assessment:** n/a (correct skip).
- **Recommendation:** none, correct as is.

### Control 2: Process (`scripts/`)
- **Status:** ABSENT+NOT-NEEDED → CORRECT SKIP
- **Evidence:** `scan_skill.py` reports `2_process.present: false`. The only deterministic-ish logic owned by this skill is slug generation, described in prose at `SKILL.md:28` ("kebab-case from trade name, no accents, no punctuation, max 5 words").
- **Skip is correct because:** the orchestration logic (phase table, dispatch prompts, verdict math) is exact and low-drift as prose; there's no repeated deterministic transform expensive enough to justify a script. Tool/MCP steps (`Task` dispatch) are correctly "process-pinned" by naming the exact `subagent_type` and inputs per platform (`SKILL.md:47-59`).
- **Assessment:** mostly fine, one low-drift edge: the slug rule ("no accents, no punctuation, max 5 words") is under-specified enough that two runs about the same company with slightly different phrasing of the name could produce two different slugs, which would silently break the folder-existence resume check in Phase 1 and "Resume after interruption." See P3 finding below.
- **Recommendation:** tighten the prose rule rather than add a script (a script would be over-engineering for a one-line transform): state explicitly "strip diacritics via NFKD normalization, lowercase, replace all non-alphanumeric runs with a single hyphen, take the first 5 whitespace-separated words of the *trade name only*" so the same company name always maps to the same slug regardless of phrasing in the user's request.

### Control 3: Output (`assets/`)
- **Status:** PRESENT+WIRED+NEEDED
- **Evidence:** `assets/report-template.html` (1827 lines, ~120 `{{SLOT}}` placeholders). Referenced at `SKILL.md:75` as `template_path: ${CLAUDE_PLUGIN_ROOT}/skills/g14-company-analysis/assets/report-template.html`. **Note on the scan output:** `scan_skill.py` flags this control as `orphan: true` / `wired_in_skillmd: false` — verified this is a **false positive**. The scan's wiring regex requires `assets/` not immediately preceded by another `/`, but the real reference is `.../g14-company-analysis/assets/report-template.html`, where `assets/` is preceded by `/`, so the lookbehind rejects a match that is, in fact, a valid reference. Confirmed by reading `SKILL.md:75` directly: the control is genuinely wired.
- **Assessment:** the template is a literal slot-fill target, output destination and filename are both deterministic (`research/{slug}/{slug}.html`, stated at `SKILL.md:36` and `SKILL.md:77`), and `SKILL.md:167` explicitly forbids ad-hoc structural changes ("The synthesizer doesn't invent structure — only fills slots. Do not modify the template ad-hoc."). That's the control done well on the two axes that matter (fixed structure, deterministic destination+naming).
  One real weak spot: the banner block inside the template itself carries a stale, contradictory instruction. `assets/report-template.html:1169` reads (translated): *"OPTIONAL BANNER — if tests return warnings, the orchestrator inserts this block; if tests are clean, DELETE it entirely."* But the actual mechanism used elsewhere is different and inconsistent with this comment on two counts: (a) `plugins/research/agents/research-synthesizer.md:91-99` instructs the synthesizer to *always* wrap the banner in `<!-- BANNER-OFF ... BANNER-OFF -->` markers at fill time (never delete it), and `SKILL.md:117` (Phase 5, Case B) expects to find those exact markers to strip; (b) the template's own comment presupposes test results are known at fill time, but Phase 3 (synthesis) runs *before* Phase 4 (grading) — the synthesizer cannot know yet whether tests will be clean, so "delete if clean" is not even executable at the point this comment addresses. If the synthesizer follows the template's own comment instead of the agent file's instruction, the banner block would be deleted outright, and Phase 5's Case B edit ("remove the two marker lines") would have nothing to uncomment — a report flagged with warnings could go out with no visible banner.
- **Recommendation:** edit `assets/report-template.html:1169-1172` to bake the `<!-- BANNER-OFF ... BANNER-OFF -->` wrapper directly into the committed template (around the existing `<div class="banner">` block) and replace the misleading Spanish comment with one that states the real contract: the synthesizer only fills `{{BANNER_MESSAGE}}` and must preserve the wrapper; the orchestrator strips the markers in Phase 5 only if the grader verdicts warrant it. This removes the need for the synthesizer to reconstruct the exact marker syntax from prose every run and eliminates the contradiction entirely.

### Control 4: Speed (`agents/`)
- **Status:** PRESENT+WIRED+NEEDED (satisfied externally, not as a skill-local folder — correctly so)
- **Evidence:** no skill-local `agents/` folder (`scan_skill.py`: `4_speed.present: false`), but `SKILL.md:41-69` (Phase 2) dispatches 11 `Task` calls with `subagent_type` set to plugin-root agent names (`website-crawler`, `google-researcher`, etc., confirmed present in `plugins/research/agents/`), explicitly "in the same assistant turn, in a single block" (`SKILL.md:43`). Phase 4 (`SKILL.md:85-100`) fires `hallucination-grader` + `source-validator` the same way.
- **Assessment:** correct per the plugin's architecture (`plugins/research/CLAUDE.md`): a skill-local `agents/` folder here would either duplicate plugin-root agent content or require the skill-nested-agent registration workaround that the *audit* plugin uses for a different reason. Since these agents are registered plugin-root agents (not skill-nested instruction files), dispatch by `subagent_type` name is the correct mechanism and model/effort declared in each agent's frontmatter (confirmed: `website-crawler` haiku/low, `research-synthesizer` haiku/medium, `hallucination-grader` haiku/high, `source-validator` haiku/medium) auto-applies without the skill needing to restate it. Both fan-outs are genuinely parallel, matched to the independent-unit shape (11 platforms, 2 orthogonal quality checks), and neither is large/unbounded enough to warrant a dynamic Workflow. `SKILL.md:176-177` allows a one-off `sonnet` escalation for a single failing synthesis/grading call, with a stated reason each time — consistent with the plugin's stated exception ("skills may escalate a single failing call to sonnet as a one-off retry, but never default to it"), so this is not a finding.
- **Recommendation:** none on the fan-out shape itself. See the Phase 2 retry/stop-step gap below (cross-cutting, error handling) for the one related gap.

### Control 5: Tests (`tests/`)
- **Status:** PRESENT+WIRED+NEEDED (satisfied externally, not as a skill-local folder — correctly so)
- **Evidence:** no skill-local `tests/` folder, but `SKILL.md:85-141` (Phase 4-5) mandates two fresh-context graders (`hallucination-grader`, `source-validator`) run in parallel before delivery, each with a JSON verdict and hard, externally-checkable pass criteria (claim traceability to findings files; URL reachability), and a three-way delivery decision (clean / warnings / withhold) driven by those verdicts.

- **Recommendation:** none on the gate's structure. See the Phase 2 retry/stop-step gap below — a permanently-missing findings file has no defined fallback before it reaches the graders.
