# Skill audit: g14-full-audit

**Target:** `/Users/pablovgdev/g14/projects/galileo14-plugins/plugins/audit/skills/g14-full-audit`
**Audited:** 2026-07-09 · single-pass manual audit against the five-controls rubric (no fresh-grader quality gate this run)
**Conformance:** Adequate (0 P1 gap, 2 P2 issues, 1 P3 polish item)

## Verdict

The skill is well built and correctly follows the plugin's documented exception: it fans out to the five existing plugin-root lens agents in parallel and adds nothing but the cross-lens consolidation, exactly as `plugins/audit/CLAUDE.md` prescribes. Triggering, frontmatter, model/effort/tools discipline (never overridden), and the two report templates (md + html, both fixed-slot, both saved to a deterministic `<target>/reports/full-audit-<timestamp>.*` path) are all solid. The two real gaps are both about what happens when something goes wrong rather than the happy path: there is no defined behaviour if one of the parallel lens `Task` calls fails mid-run (risking a report that silently claims "5 of 5 lenses ran" when one didn't), and nothing enforces the skill's own hard rule that the `.md` and `.html` outputs must not drift apart in content. Neither is a structural five-controls gap — both are best-practice error-handling gaps worth a small, concrete fix.

## Skill profile

What it does: asks the user which of five existing audit lenses to run (or infers them from the request), dispatches one `Task` per chosen lens agent (`security-auditor`, `scalability-auditor`, `architecture-auditor`, `clean-code-auditor`, `database-auditor`) in parallel in a single message, then consolidates the independent reports into one combined markdown + HTML deliverable.

Nature (drives which controls are needed):
- Input variability: none of its own — it reads only its own two fixed templates; all lens-specific "what to look for" is owned by the plugin-root agents it dispatches to (by design, per `plugins/audit/CLAUDE.md`).
- Process: the target-resolution/path-building logic is a few inline, deterministic bash lines already scripted literally in `SKILL.md` (not prose reasoning); the consolidation step is genuine per-run synthesis (pooling, ranking, narrative) that cannot be pre-scripted.
- Output: fixed shape — two literal `{{slot}}` templates (`assets/report-template.md`, `assets/report-template.html`) that must report identical findings/counts, only the rendering differs.
- Parallelisable work: yes, and already exploited — up to 5 independent lens audits, dispatched as one message with one `Task` call per lens, "all in the same turn so they run concurrently."
- Correctness risk: real — the deliverable is a security/scalability/architecture/etc. audit report; wrong-but-plausible findings and lens-completion claims are both things a human could act on without re-verifying.
- Runtime and scaling: bounded fan-out (max 5 units, never large/unbounded), so plain parallel `Task` dispatch is the right mechanism — a dynamic Workflow would be over-engineering here.
- Length and resumability: 5 pipeline steps — under the ~8-step threshold where checkpointing becomes worth its cost; a correct skip.

## Per-control findings

### Control 1: Input (`references/`)
- **Status:** ABSENT+NOT-NEEDED → CORRECT SKIP
- **Evidence:** `scan_skill.py` → `controls.1_input.present: false`; no external facts, feeds, or fixed schemas are consumed directly by this skill.
- **Needed because / Skip is correct because:** the skill pulls no facts of its own — all lens-specific "what to look for" content is deliberately owned by the plugin-root agents (`plugins/audit/CLAUDE.md`: "The audit lens lives in the agent. The skill is a thin runner" — extended here to "fans out, doesn't duplicate"). Adding a `references/` folder here would duplicate agent content, which the plugin's own architecture doc explicitly forbids ("never build lens content directly inside `g14-full-audit`").
- **Assessment:** correct skip.
- **Recommendation:** none, correct as is.

### Control 2: Process (`scripts/`)
- **Status:** ABSENT+NOT-NEEDED → CORRECT SKIP
- **Evidence:** `SKILL.md` lines 34-40 embed the only deterministic logic (target canonicalisation, timestamped path construction) directly as 4 literal bash lines, not prose the model re-derives each run.
- **Needed because / Skip is correct because:** the logic is small enough (4 lines) that inlining it in `SKILL.md` already satisfies "method captured as code that's run, not prose that's reasoned" — extracting it to a `scripts/` file would add a file for no determinism gain. The one part that can't be scripted (pooling/ranking/synthesizing across lenses in step 4) is genuinely novel-per-run judgement, correctly left as guided prose.
- **Assessment:** correct skip, though see the Control 5 / cross-cutting finding below about a small missing verification script.
- **Recommendation:** none for the core pipeline; see Prioritised improvements #2 for a narrow, optional addition.

### Control 3: Output (`assets/`)
- **Status:** PRESENT+WIRED+NEEDED
- **Evidence:** `assets/report-template.md` and `assets/report-template.html`, both literal `{{slot}}` templates; `SKILL.md` step 4 (lines 75-88) names both files by exact `${CLAUDE_PLUGIN_ROOT}` path, says "fill every placeholder," and forbids renegotiating structure ("Hard rules," line 115).
- **Assessment:** well built. Both templates share identical structure/slots (only the rendering differs, per the explicit hard rule), both use fixed severity vocabulary (CRITICAL/HIGH/MEDIUM/LOW/INFO kept in English on purpose, "greppable"), and the HTML version is self-contained (inline CSS only, `prefers-color-scheme` dark-mode support, no external fonts/CDN — matches the artifact self-containment requirement). Output destination and naming are deterministic: `$TARGET/reports/full-audit-$TIMESTAMP.md` / `.html`, built in step 1 before any agent is dispatched — exactly the "structured, repeatable storage" the rubric asks for.
- **Recommendation:** none, correct as is.

### Control 4: Speed (`agents/`)
- **Status:** ABSENT (locally) but NEEDED-and-satisfied externally → ✅ matches the plugin's documented exception, not a gap
- **Evidence:** `plugins/audit/CLAUDE.md` — "It creates no new agent. All five `subagent_type` values it dispatches to... are the same plugin-root agents the standalone skills use." `SKILL.md` step 3 (lines 52-73): "Send one message with one `Task` tool call per chosen lens, all in the same turn so they run concurrently," plus an explicit table mapping lens → `subagent_type`, and "Do NOT override any agent's model/effort/tools — they are fixed in each agent's frontmatter for a reason."
- **Assessment:** this is the control done correctly under the plugin's stated exception. A local `agents/` folder here would violate the "no new agent" rule and duplicate lens content, which is explicitly disallowed. The five plugin-root agents are already registered (not skill-nested), so the registration caveat that normally applies to nested `agents/*.md` files does not apply — `Task` dispatch by `subagent_type` name works directly. Model/effort/tools stay untouched by this skill, as required.
- **Recommendation:** none on parallelisation itself. See Prioritised improvements #1 for the one real gap in this area: no defined behaviour when a dispatched lens `Task` fails.

### Control 5: Tests (`tests/`)
- **Status:** ABSENT; ambiguous rather than a clean GAP or a clean CORRECT SKIP
- **Evidence:** `scan_skill.py` → `controls.5_tests.present: false`. The sibling single-lens skills (`g14-security-audit`, etc.) also carry no `tests/` folder — confirmed by listing `plugins/audit/skills/g14-security-audit/` (only `assets/` and `SKILL.md`). This is a consistent, deliberate plugin-wide pattern: correctness is meant to come from each lens agent's own grounding instructions (file:line citations, "observed in the code"), not an independent fresh-grader pass, and a human is expected to read the report before acting on it.
- **Needed because / Skip is correct because:** per the decision-table trigger, Control 5 is needed "when the output makes claims that could be wrong-but-plausible... AND no human reviews every run." An audit report is exactly that kind of claim-bearing output, which argues for some verification; but this is a plugin-wide design choice already made consistently across all five single-lens skills (none of which have `tests/` either), not something unique to `g14-full-audit` to fix in isolation, and a human is the expected reviewer of an audit deliverable before it drives action.
- **Assessment:** not flagging a full Control 5 (fresh-grader `tests/` folder) as a gap here, since that would mean redesigning the whole plugin's verification approach, out of scope for a single-skill fix. But the one claim that is genuinely new to *this* skill and mechanically checkable — that the `.md` and `.html` renderings report the exact same findings and counts — has no verification at all despite `SKILL.md`'s own hard rule demanding it. That narrower, mechanical check is worth adding regardless of the broader Control 5 question.
- **Recommendation:** see Prioritised improvements #2.
